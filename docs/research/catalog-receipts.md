# Catalog receipts and ownership research

Checked 2026-10-06. All runtime pass/product IDs remain zero.

- [MarketplaceService](https://create.roblox.com/docs/reference/engine/classes/MarketplaceService): use one server `ProcessReceipt` callback for all developer products. Roblox may deliver receipts concurrently, replay them after an acknowledged grant, or invoke them on rejoin. `NotProcessedYet` has no timed platform retry; a later purchase or rejoin triggers another opportunity. `PromptProductPurchaseFinished` is never grant authority.
- The same API reference documents cached `UserOwnsGamePassAsync` results. `PromptGamePassPurchaseFinished` updates its cache; external purchases may take minutes to propagate. Server purchase completion reflects the platform outcome. Keep positive grants on stale negatives/errors, refresh every 120 seconds and provide the existing manual refresh. A zero ID must never reach Marketplace APIs.
- [Player data and purchasing](https://create.roblox.com/docs/cloud-services/data-stores/player-data-purchasing) and [Data stores](https://create.roblox.com/docs/cloud-services/data-stores): grant, PurchaseId and player progression must share the durable profile write. UpdateAsync transforms can replay, so grants are constructed outside the transform; transforms only verify the lease and write an immutable snapshot. Never acknowledge an in-memory Studio fallback profile.
- [Staff purchasing implementation article](https://devforum.roblox.com/t/implementing-player-data-and-purchasing-systems/2839941) and the existing [June owned-pass replay research](audit2-marketplace.md) inform cross-session locking and idempotent entitlement effects. The direct June forum URL returned a JavaScript challenge during this session; current official Marketplace docs independently establish the behavior used here.
- [Developer products](https://create.roblox.com/docs/production/monetization/developer-products) includes externally purchased receipts. Receipt payloads provide no historical income snapshot or prompt correlation token. In-experience prompts therefore persist a server-calculated quote before opening; unquoted external receipts use the rate at first successful processing. The catalog discloses this operational distinction; disable external sales if exact pre-purchase income quotes are required.
- Current Marketplace docs also list `BindReceiptHandler` as an alternative. This task explicitly requests `ProcessReceipt`; no second binding is installed. The [release notes index](https://create.roblox.com/docs/release-notes) was checked without finding a contract change that requires replacing it.
- [Rojo project format](https://rojo.space/docs/v7/project-format/) and [StyLua](https://github.com/JohnnyMorganz/StyLua) checked for the build/format workflow. Whole-tree check uses Windows line endings. Selene's existing missing-standard-library limitation must be reported, not hidden.

Bounded dedupe cannot safely forget old PurchaseIds: Roblox does not promise a maximum replay age. Keep 128 entries in the profile; before evicting an acknowledged old entry, persist a permanent tombstone in `ToiletRNG_Receipts_v1` (Studio: `ToiletRNG_Receipts_Studio_v1`). Consult tombstones with UpdateAsync to avoid stale GetAsync negative caches. A crash before/after archiving leaves the original receipt in at least one durable location; a failed archive prevents eviction/new grant. The archive is intentionally unbounded across distinct purchases while each player profile stays bounded.

Existing 180-second session leases, whole-profile replacement guard, immutable retries and fail-closed saves remain the transaction foundation. Early rejoin receipts wait up to 30 seconds for profile readiness. No external administrative restore or indefinitely stalled backend durability guarantee is claimed.
