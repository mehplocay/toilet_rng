## Ownership, races and cleanup

- Display counts reserve inventory rather than creating item copies. Selling excludes all reservations; removing a display changes no count. Collection is lifetime discovery, not spendable inventory. All configured pools end in Poop and every completed flush awards one item, independently checked rarest first.
- Discovery events deduplicate per-player flush sequence, refresh a single expiry and stay at x2 instead of exponentially stacking. Personal daily x2 combines multiplicatively with toilet/event luck as current code intends; repeated claims cannot extend it. With zero pass IDs the current maximum is 1.3 x 2 x 2 = 5.2. No client sends luck, timestamps, pool, price or reward amounts. The future strongest-event/capped monetization design is not implemented.
- A save copies all inventory/coins/display/reward fields before yielding. Gameplay during an ordinary save is included by the later final snapshot; Close blocks Get before waiting for an outstanding save. Concurrent PlayerRemoving/BindToClose calls must not release or clear a later load's state. A lock conflict cancels instead of saving defaults in live play; Studio fallback is explicitly nonpersistent.
- Per-player tables reviewed: DataService Profiles/Saving/Closing/NoPersistence; RateLimiter.Players; FlushService nextFlush; Monetization Owned/Auto; Event Seen; World Assigned/plot Owner/Profile. Existing cleanup clears these on removal; asynchronous pass lookup checks Parent before repopulating Owned. World tween links/value instances and transient models are destroyed on completion; particle/sound debris is time-bounded. Client tutorial disconnects its listeners; model idle entries disconnect on destruction. No confirmed unbounded per-player leak in the current lifecycle; new lifecycle tables need explicit cleanup regression checks.
- World geometry is anchored; only configured assets are built, with no client-directed require, instance deletion, asset ID, external HTTP or arbitrary table persistence. World loops have waits (auto 0.5s, board/display pages 10s, autosave 60s); visual models use fixed/config-bounded loops and five physical display stands even for 100 saved slots. Headless part-budget checks are available; real mobile/replication profiling remains necessary. Client idle/UI loops live for the local session.
